# Security model

TailShare is experimental. The implementation has tests and dependency checks, not an independent security audit.

## Trust boundaries

The sender trusts the static application code and the browser, selects a finite set of files, then explicitly starts sharing. The recipient trusts the separately delivered invitation to identify the source of the share. Opening or pasting a link connects and displays the validated manifest for confirmation; no file contents are requested until the recipient confirms or explicitly downloads from the browser. Key-only connections open the file browser without prompting or downloading. There is no account, identity directory, out-of-band fingerprint confirmation, or protection against a compromised endpoint or hostile browser extension.

Tailcat provides authenticated WireGuard encryption. Its current addresses include a preshared key. TailShare adds an independent 32-byte random application token, required before a peer receives the manifest. The full address **and** token are credentials. Public relays observe network identities, timing, and traffic volume, but not application plaintext. The static host sees requests for application assets. The relay-map service sees requests for its public map.

## Data access

For browser-hosted shares, only selected browser `File` objects enter a session map. That wire protocol never accepts an OS filesystem path, directory handle, arbitrary URL, or remote command. Requests reference a random opaque entry ID, checked against the share's exact file map. There is no upload endpoint, remote write operation, preview HTML, archive extraction, or executable-content rendering.

Received metadata is validated before rendering or opening a destination: version, cardinality, unique IDs, file lengths, integer bounds, parent directories, case-insensitive collisions, Unicode normalization, path depth/length, control characters, bidirectional overrides, Windows device names, and unsafe path characters. React renders file names as text. Downloads have an opaque binary MIME type. ZIP output uses only validated relative paths. Separate-file disk batches go in a newly named destination folder to prevent accidental overwrite of unrelated files.

## Resource controls

Frames are bounded before allocation. File data uses 64 KiB frames and pull-based reads/writes. A coalesced transport write is limited to 64 KiB plus the five-byte frame header; reads remain limited to 64 KiB and the decoder handles fragmentation. Sender reads slices; receiver hashes incrementally. Native writable streams are committed only after SHA-256 verification; on failure they are aborted. ZIP commits only after all selected entries pass verification. In-memory sinks have a 256 MiB cap; batches are capped too. ZIP32 output has a conservative size bound below 4 GB. At most four simultaneous connections per share are allowed; the WASM bridge caps registered streams. Authentication, connection setup, write, idle, and transfer timeouts bound stalls. There is no promise of resistance to volumetric denial of service.

The network/WASM runtime runs in a dedicated same-origin module worker. Its private message bridge permits only named transport operations, limits pending requests to 64, and leaves cancellation notifications available when that limit is reached. It is not a cross-window messaging API or an additional security boundary against compromised application scripts. Worker failure rejects pending operations; active sessions are cleared instead of silently reconnecting. Returned byte buffers are transferred to the page; outgoing buffers are cloned so hashing/ZIP callers keep ownership. Hashing and ZIP processing stay in the page with bounded chunks. No shared memory, cross-origin isolation, service worker, or persistent file cache is introduced.

Engine preparation after file selection fetches same-origin static assets only. Runtime/WASM URLs are derived from a shared build hash embedded in the application; their origin is checked before loading and deployment validation recomputes the pair hash. This is cache consistency, not protection from a compromised host. Screen wake lock is opt-in, released when inactive/hidden, and does not grant background execution or access to additional files.

## Credential lifecycle

Invitations use URL fragments; browsers do not include fragments in HTTP requests or referrer headers. The app consumes and removes the recipient fragment immediately, stores credentials only in memory, and does not use localStorage, cookies, telemetry, or third-party scripts. This does not erase a previously copied link, messages, screenshots, browser sync, extensions, or history captured before removal. Stop and timed expiry close the listener and active streams. A null deadline means no time expiry; it does not survive the sender tab closing or refreshing. Limits apply to both link and key. For usage expiry, the host reserves a use atomically after authentication and before sending metadata; invalid credentials do not consume uses. Limits are 1–1,000 authenticated connections, not distinct people. Exhaustion rejects new connections while admitted recipients can finish; the listener closes after the final recipient leaves. Reconnecting consumes another use. Time checks also run at handshake, file request, chunk transfer, and before recipient commit, so delayed background timers do not grant continued access on resume. Recipients may observe disconnect only after a pending operation times out. Bytes already received or saved cannot be revoked.

## CLI receiving

A bare `tc…` address selects the CLI adapter; malformed browser invitations are never retried without their application token. CLI addresses must include a WireGuard preshared key and reference the default public relay regions. They are cleared from the input on connection and kept in memory only. Do not publish CLI keys or save them in source, test fixtures, screenshots, or logs; the publication scanner includes a bare-address rule.

The receiving flow connects only through Tailcat to port 22, negotiates SSH and its SFTP subsystem, and issues read-only requests. WireGuard authenticates the server using the invitation's node key and preshared secret. As in upstream `tailcat ls`, the SSH host-key callback relies on that already-authenticated tunnel, not an OS known-hosts file. This assumption applies only to Tailcat sockets; the adapter is not an arbitrary TCP/SSH client. Receiving does not import login keys or passwords, open a shell, execute commands, forward ports, or upload/change files. The sender should run a current `tailcat serve --key=new --files=./shared:ro files` with a deliberately chosen directory. The app cannot independently attest which CLI command a peer ran or enforce read-only access by other clients holding its key.

CLI listings are requested one directory page at a time. No complete manifest or global map of visited files is retained, and no total-entry cap applies to CLI browsing. A dedicated read-only SFTP v3 channel handles OPENDIR/READDIR/CLOSE; file transfers and metadata checks use the existing SFTP client over the same authenticated SSH/Tailcat connection. Incoming packets are limited to 256 KiB before allocation. Each page processes at most 128 names and returns at most 1 MiB of JSON metadata, retaining at most one partial wire packet per cursor. Counts, strings, attributes, request IDs, handles, and status packets are validated before use. At most 34 directory cursors can remain open, supporting one browsing cursor plus depth-first traversal within the existing 32-segment path bound. Cursors rotate on every page and are single-use; closing, EOF, cancellation, or disconnect releases them.

Each listed file or folder carries a capability authenticated with HMAC-SHA-256 and a fresh random per-session secret. It binds the original remote path, kind, size, and modification time. JavaScript submits these capabilities rather than arbitrary remote paths; the Go bridge verifies them before browsing a child or opening a file, and capabilities from another session are rejected. The fixed empty root identifier addresses only the served root. Browsing caches four pages, remembers at most 1,024 recently issued entry records, and retains only the ancestor path for breadcrumbs. Recursive downloads retain a bounded page per ancestor and respect file-write backpressure. The fixed page and cursor budgets replace the previous global 10,000-entry/16 MiB listing budgets.

Connection setup and each listing operation have a 60-second deadline. Cancellation closes the socket to release pending operations. A page-side 65-second fallback rejects unanswered requests and ignores late results; browser suspension can delay timers. Files stream in batches capped at 256 KiB, with at most eight concurrent 32 KiB SFTP requests, a 120-second file-operation deadline, and a 15-minute idle connection deadline. The ordinary portable-path, file-size, memory, and transfer checks remain in force. Browser-hosted selections and browser-to-CLI uploads still use their existing 10,000-entry manifest limit.

Folder downloads traverse unopened descendants only when requested; a whole-share snapshot and complete size preflight are unavailable. Incremental ZIP output enforces 4 GB, 65,535 entries (ZIP32), and 8 MiB of central-directory metadata estimates, and rejects duplicate/case-colliding paths and file/directory conflicts across pages. A failed ZIP aborts its sink. Separate disk downloads create a fresh destination folder and refuse existing file paths instead of overwriting earlier output. Memory-backed separate downloads stop at the aggregate 256 MB batch bound. Completed files and directories can remain after cancellation, error, or a later limit failure. There is no automatic retry, rollback, or resume. Directory contents can change between pages; refreshing restarts enumeration, and cached or reread pages do not form a snapshot.

Symbolic links and special files are skipped. Ancestor directories and files are checked again before opening, and file length and modification time are checked before committing. The CLI's rooted file service uses `os.Root` to confine paths; client-side checks alone cannot eliminate remote filesystem races. Keep the source files stable during transfer. CLI/SFTP does not supply a separate sender checksum or immutable snapshot; same-size, same-timestamp edits may be undetectable. Authenticated SSH/WireGuard protects bytes in transit. The interface describes CLI files as downloaded instead of SHA-256 verified. Failed, changed, cancelled, and incomplete transfers abort their current sink.

Browser-host time/use limits do not apply to a CLI share. Its process and CLI access controls determine availability. Stopping the CLI interrupts access; restarting with a saved key can restore previous key holders' access. Use Refresh folder to restart its listing. Receiving cannot browse write-only drop boxes; the separate sending flow below supports them. SSH login authentication, custom relays, and full addresses embedding relay metadata remain unsupported.

## CLI uploads

The Send files flow offers an explicit Tailcat CLI destination. Only selected browser `File` objects are streamed, only after the user supplies a bare receiver key and clicks Send to CLI. It uses the same authenticated Tailcat TCP 22 connection and SSH/SFTP client, without shell commands or OS credentials. The key is cleared on starting and retained only in memory. Browser invitations, arbitrary URLs, command strings, unprotected addresses, and custom relay addresses are rejected as receiver keys. No receiving-browser upload endpoint or hosted storage is introduced.

The browser snapshots and validates its selection before connecting. Go independently validates the bounded upload plan before any remote write, and subsequent operations name only plan entry IDs. Paths exclude traversal, absolute paths, unsafe characters, device names, and case-insensitive collisions. The upload plan is capped at 4 MiB and 10,000 entries, and files stream one at a time in acknowledged 256 KiB batches of at most eight concurrent 32 KiB SFTP requests with a 120-second operation/inactivity timeout. Connection and folder setup have a 60-second deadline. Local reads, chunks and file lengths are checked; ZIP is streamed under a conservative 4 GB bound. Zero-byte files and available empty directories are supported.

Default `tailcat recv` is a flat write-only drop box that chooses unique names. Separate-file mode discards paths explicitly; ZIP preserves them inside an archive. Tree mode requires `--accept-dirs` and creates a new random `TailShare-…` parent with newly created descendants. Failed directory creation is never treated as permission to reuse an existing path. Ancestor directories are checked for symlinks, and files are opened with WRITE/CREATE/EXCLUSIVE, never truncate or append, even on a writable SFTP service. TailShare never lists/reads the receiver's inbox, removes files, renames files, or changes permissions. The intended rooted CLI uses `os.Root`; a remote owner can still race changes to their filesystem. The app cannot attest which server command a key belongs to, so use a dedicated inbox and exchange its key privately. `--accept-dirs` permits directory stats and leaks more path information to key holders than flat mode.

Completion requires successful writes, acknowledged file close, and the remote size matching bytes sent. This is authenticated transport delivery, not an independent SHA-256/read-back or filesystem durability guarantee. Cancellation closes the tunnel and stops subsequent reads/writes. The drop box cannot delete or roll back uploads: completed files, partial files, and directories may remain after failure or cancellation, including noncontiguous partial data from a pipelined batch or when a final acknowledgement is lost. There is no automatic retry; recipients must inspect the inbox before manually retrying to avoid duplicates. Any holder of a receiver key can consume disk space until the CLI is stopped. The process lifetime, not the browser-share expiry dropdown, controls receiver access.

## Hosting

Deploy the static production output over HTTPS. Do not expose a Vite development server publicly. The production page includes a restrictive CSP: self-hosted script/style/fonts, `wasm-unsafe-eval` for WebAssembly (no JavaScript unsafe-eval), no objects/forms/base rewriting, and an explicit list of relay endpoints. The development server removes that meta CSP solely for Vite's injected development scripts/styles.

`public/_headers` provides additional HTTP headers for hosts supporting that convention. On other hosts configure equivalent CSP including `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`. A meta CSP cannot enforce `frame-ancestors`. When changing the relay map, review the endpoint allowlist in both `index.html` and `_headers`. Do not add arbitrary endpoints from invitation/query parameters.

The dedicated worker is loaded from a same-origin URL and [does not inherit the document's CSP](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers#content_security_policy). Cloudflare's catch-all `_headers` rule supplies a CSP response header for the worker script, including its relay endpoint restrictions. GitHub Pages cannot apply this header configuration: its page meta CSP restricts which worker can be created, but does not restrict requests made inside that worker. The worker still uses the application's fixed relay-map URL and transport implementation. Use a host with configurable response headers if worker-level CSP enforcement is required.

Pin dependencies and commit lockfiles; rebuild WASM with the matching runtime. Check npm and Go advisories before deployment. Serving malicious JavaScript from a compromised host can defeat browser-side encryption; no cryptography in this app fixes a compromised origin.

## Repository and deployment privacy

This application needs no runtime secrets. Never put credentials in frontend environment variables, source, or public assets: anything shipped to a browser is public. Ignore rules exclude local environment/authentication files, private keys, editor/tool state, and test captures. Ignoring a file does not remove it if it was already tracked, committed, or uploaded. Git author and committer metadata also require a deliberate public identity; see the first-commit instructions in the README.

The deployment check permits only the reviewed static files, compiled JavaScript/CSS, and bundled fonts. It rejects extra files, source maps, and symlinks because Vite copies `public/` independently of Git ignore rules. The WASM build uses `-trimpath` and strips debug data to avoid embedding local source paths. Gitleaks scans source snapshots and the production bundle in CI, with additional invitation and home-path rules. Because the scanner normally skips binary content, a separate step extracts and scans readable WASM strings. CI scan output is redacted. These are pattern-based safeguards, not a guarantee that arbitrary personal data will be recognized. Review the staged diff before publishing; the CI snapshot scan does not audit older commits or commit identities.

## Known constraints

SHA-256 checks accidental corruption and protocol consistency, not malicious sender content. The trusted sender can generate matching hashes for malicious files. Browsers vary in their download handling, file-system support, storage quotas, and behavior while backgrounded. TailShare cannot verify that a fallback download was ultimately accepted or persisted by the browser. Failed file writes may leave an empty destination entry or empty batch folder; no partially verified file contents are intentionally committed. Resume, persistent key storage, malware scanning, and mobile background transfers are out of scope for this version.
