# File sharing console
Mode: Operate. Primary task: select local files and either open a browser share and copy its link, or send them explicitly to a Tailcat CLI receiver key; recipients using a link confirm the file list to start downloading the whole share, while browser-key and Tailcat CLI-key recipients use the same receive field and browse first. The user's neon retro cyberpunk brief binds the visual direction. Code-first confirmed.

## Direction contract

The connection rail names the CLI source, explains that the sender's command must stay running, and describes opening folders on demand, paging through entries, and using “Refresh folder” to reload the current listing. In Send files, the destination selector also offers “Tailcat CLI · receiver key”: select and inspect files or folders, paste the recipient's key, choose separate files, a streaming ZIP, or a folder tree, then explicitly choose “Send to CLI.” Pasting the key alone sends nothing, and starting clears it from the field. The session rail tells the recipient to create an inbox and run `tailcat recv --key=new ./inbox`, adding `--accept-dirs` only for tree mode. It explains that no share link is created and that the receiver acknowledges writes and file size without a read-back checksum. Live upload progress and Cancel reuse the console feedback strip; completion reports files, ZIP, or the created folder after acknowledgement. Cancellation and failure warn that completed or partial files may remain, direct the recipient to inspect the inbox before retrying, and require a fresh explicit transfer. ## Paged CLI folder browsing

Connecting to a `tailcat serve` file service loads only the first root page. Opening a folder requests that folder's entries; unopened descendants are not scanned for browsing. A page processes at most 128 names, with Tailcat normally returning 100. Four pages are cached, and older pages are reread from the beginning when revisited. Entries are sorted within each page. There is no total CLI directory or served-tree entry cap, and the live listing is not an immutable snapshot.

Below the bounded file-row region, “Previous page,” the current page number, “Next page,” and “Refresh folder” reuse secondary buttons and muted tabular text. A thin slate rule separates this group from the rows. Controls wrap on small screens, retain 44px minimum targets, and use the existing orange focus outline. Muted help text explains that folders load when opened, filtering and selection apply to the page, and folder downloads include unopened subfolders. The first page disables Previous; the final page disables Next; pending work disables navigation. Refresh restarts the current folder at its first page. Successful page changes, folder navigation, and refresh clear filtering and selection and return the file list to the top.

“Filter this page” and “Select visible items” describe their scope explicitly. The summary reports the number of items on the loaded page and bytes in its listed files, never an implied count or size for the entire tree. Folders remain selectable even when no files are listed. With a selection, the actions read “Download selected” and “ZIP selected items”; selected folders include their unopened descendants. With nothing selected, downloading covers the current folder and its descendants, with “Download folder as ZIP” below the root and “Download all as ZIP” at the root.

Downloads discover and stream descendants incrementally after the user chooses a destination. ZIP and supported directory saving preserve empty folders; memory-backed separate downloads save files only. Existing file progress remains based on bytes actually transferred, and final counts come from completed traversal. ZIP retains its 4 GB, 65,535-entry, and 8 MiB metadata bounds; memory-only downloads retain the 256 MB limit. Browser-origin selections and CLI uploads retain their 10,000-entry cap. A failed ZIP is discarded; separate downloads may leave earlier files and created directories. Cancellation disconnects the session and interrupts pending reads; listing timeouts and recoverable folder errors use the existing feedback strip. Paths, per-session signed entry identifiers, and rotating bounded cursors are validated without adding a backend or dependencies.

## Transfer readiness and screen wake control

Selecting readable files starts preparing the Go/WASM transfer engine in a worker. This loads static transport assets without opening a relay or peer connection. The session rail keeps a compact cyan status line in every phase: “Transfer engine loads on selection.” while idle; “Preparing transfer engine,” “Downloading transfer engine,” or “Starting transfer engine” followed by an ellipsis while loading; “Transfer engine ready.” when ready; and “Transfer engine needs attention.” on error. Its one-line minimum height preserves the status row when loading completes, avoiding the layout collapse that could shift the share action through scroll-position clamping. A loading failure adds its detailed message below the status in orange and offers an underlined cyan “Retry transfer engine” action. Retry prepares the engine again; it does not itself create a share or send files.

The same group sits above the session heading, to the right of the console on desktop and below it in the single-column layout. A thin slate divider separates it from the remaining session details. The native “Keep screen awake” checkbox starts unchecked, uses the existing cyan accent and orange focus outline, and has a 44px-tall label target. Muted help text beneath it is associated with the checkbox and announces state changes as status content; the retry action also has a 44px minimum height.

Screen wake lock is optional and requested only when enabled, the page is visible, and a browser share, file download, or CLI upload is active. Checking it before activity shows that it is waiting. Help text distinguishes requesting, active, released, unavailable after a failed or denied request, and unsupported states; unsupported browsers disable the checkbox and tell the user to keep the screen on manually. Ending activity, hiding the page, or unchecking releases the lock. Returning to the visible page requests it again while the option remains enabled and activity continues. A system release produces a visible warning without repeatedly requesting a new lock. Even when held, the copy asks the user to keep the page visible; it makes no promise of background execution or uninterrupted transfer.

Transfer progress retains the console's filename, actual transferred/total bytes, and thin cyan native progress bar, labelled for upload or download. Routine presentation updates are coalesced to roughly 100ms intervals; a new file, completion, or cleared progress is delivered immediately. This changes rendering cadence only: transfer checks and backpressure still process each chunk, and no throughput estimate or simulated progress is introduced.
